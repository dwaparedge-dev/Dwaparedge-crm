# Data model

PostgreSQL, declared in `db/tables/**/*.sql` (registered in `db/schema.ts`, built by `npm run db:sync`; triggers and views in `db/logic/`). UUID primary keys, `timestamptz` timestamps, money as `NUMERIC(14,2)`, quantities `NUMERIC(12,3)`, rates `NUMERIC(5,2)`. Business data is relational; the only JSON columns are the frozen snapshots on issued invoices (parties and document) and free-form `metadata` on the activity log.

```
users ──< clients ──< contacts
            │  ├──< sales ──< sale_items >── products
            │  │      └──< sale_milestones
            │  ├──< licenses >── products
            │  ├──< invoices ──< invoice_items            invoices >── sales (required)
            │  └──< payments ──< payment_allocations >── invoices
            └──< activity_log (all modules write here)
users ──< tasks >── task_categories, task_priorities      tasks >── clients (optional)
company_settings (single row)      document_sequences (numbering counters)
field_options (dropdown lists: table, column, key → label)
```

| Table | Purpose and key rules |
|---|---|
| `users` | Staff login. `password_hash` (bcrypt), `token_version` (bump = revoke sessions), `is_active`. Unique on `lower(email)`. `permissions TEXT[] NOT NULL DEFAULT '{}'` holds the account's own permission keys (the four `tasks.*` keys, listed in `src/lib/auth/permissions.ts`); **a new account holds none**. Migration `0017_user_permissions.sql` gave every account that existed then all four, because they had full access already. Keys are checked in code when granted (an unknown key stored by mistake grants nothing) and changed only with `npm run users -- grant` / `revoke` / `create --grant`, each of which is logged (see `activity_log`). A change applies on the user's next request. There are no role names anywhere in the data |
| `login_attempts` | Failed-login counters (hashed email/IP) for lock-out |
| `clients` | Permanent `code` (AA01 ... AA99, AB01 ... ZZ99, unique), legal/display name, GSTIN (unique, format-checked), PAN, address, state code (the name follows from it), brand names, optional bank details (bank, account no, IFSC, branch), owner, `archived_at` (= inactive). Never deleted |
| `contacts` | Per client; partial unique index = at most one primary |
| `client_documents` | Files uploaded against a client (max 4 MB each), stored in the `content` bytea column with a name and a type (`field_options` key `client_documents.doc_type`). List queries never read `content`; it is served only by the download route |
| `products` | Catalog: type, SKU (unique, case-insensitive), HSN/SAC, price, GST rate (0 = exempt), active |
| `sales`, `sale_items` | What was sold. Items copy description/price/tax from the product at the time. `quotation_number` and `agreement_ref` are printed in the invoice's Project & Agreement block |
| `licenses` | Register (`status`: pending/active/suspended/revoked; *expired* is derived from `expiry_date`). Its history is the `activity_log` filtered to the license (status change and note in `metadata`) |
| `field_options` | User-extendable dropdowns: `(table_name, column_name, option_key, option_value)`. The business table stores the **key**; the label is looked up, so renaming never touches records. Built-in rows (`is_system`) can be hidden, not deleted. A trigger rejects unknown keys on `sales.type`, `products.type`, `payments.method`, `licenses.plan`, `client_documents.doc_type`. Which columns may have options is a whitelist in `src/features/options/registry.ts` |
| `sale_milestones` | Optional billing plan of a sale: instalments by percentage or fixed amount (before GST), with a due date and a `description` (deliverables, printed on that instalment's invoice). `invoice_id` links the instalment to its invoice; it counts as billed only while that invoice is a draft or issued |
| `invoices`, `invoice_items` | **Every invoice has a `sale_id` and every line a `sale_item_id`** (NOT NULL). A trigger blocks billing more of a sale item than it is worth; another stops a billed sale item from being removed or reduced. Draft → issued → cancelled. Number allocated at issue. Snapshots (`client_snapshot`, `company_snapshot`, and `document_snapshot`: project references, the milestone billed, the full billing schedule and the billed-to-date / balance figures), per-line CGST/SGST/IGST, round-off. **Triggers** make issued rows immutable and undeletable, except `issue_date`, the optional `due_date` (NULL = not specified) and `invoice_number`, which can change only while the invoice is regenerated and never once a payment is applied to it |
| `invoice_versions` | Regenerating an issued invoice (`POST /api/invoices/{id}/regenerate`) adds a version with the client, company and project details as they are then, plus the PDF exactly as generated. Regenerating is refused while a payment is applied to the invoice. A version records the invoice number it printed (`invoice_number`): the number changes when an invoice is renumbered into the month of its new invoice date, and earlier versions keep the old one. The invoice row (number, date, amounts, original snapshots) never changes; version 1 is the original and the highest version is current. A version also records the SAC/HSN code of each line as the sale had it when the version was made (`item_codes`) and the wording of each line (`item_descriptions`), because the issued lines themselves cannot change. A trigger makes the rows permanent |
| `payments` | Receipt number, amount, method, reference, optional `sale_id` (what it was paid for). Immutable; corrected by voiding |
| `payment_allocations` | Payment ↔ invoice amounts. Reversed rows are kept (`reversed_at`). **Trigger** locks both rows and blocks over-allocation and cross-client allocation |
| `activity_log` | Who/what/when for every change, with `client_id` for the client history tab. Task history is here too (`entity_type = 'task'`, `client_id` set when the task is linked to a client, so it shows on that client's History tab); no separate history table. Task actions: `created`, `edited` (the changed fields are in `metadata`), `reassigned`, `status_changed`, `note_added`. Changes to the two task lists are `entity_type = 'task_category'` or `'task_priority'` with `created`, `updated` or `deleted`. Permission changes are `entity_type = 'user'` (`permission_granted`, `permission_revoked`, the key in `metadata`, no actor because the command line has no signed-in user); the dashboard's recent-activity feed leaves `user` rows out, because their summaries name email addresses |
| `task_categories`, `task_priorities` | The founders' own lists, edited in Settings (same idea as `field_options`, but with colours and order). `key` is a stable unique slug the code can rely on and never changes; `name` can be renamed. `colour` is `#rrggbb`. Categories carry `default_follow_up_days` (> 0, null = no repeat), copied onto a new task of that category; priorities carry `rank` (>= 1, 1 = most urgent, orders tasks inside a Desk section). `sort_order` is only the order in the pickers; `is_active = false` hides a row from the pickers. **Every starter row is `is_system`** (as in `field_options`): it can be renamed, recoloured or hidden but never deleted, and a row any task points at (`ON DELETE RESTRICT`) cannot be deleted either, only hidden. The service refuses a duplicate name (whatever the case, hidden rows included). Seeds in `db/seeds/defaults.sql` never overwrite an edited row |
| `tasks` | The Task Desk. `title` (1 to 200 characters), `description` (up to 5,000), `category_id` and `priority_id` (required, `ON DELETE RESTRICT`), `owner_id` (who must do it; null = Unassigned) and `created_by` (null for a task the system raised), both `ON DELETE SET NULL`; `client_id` optional. `status` is one of `open`, `in_progress`, `waiting`, `done`, `cancelled` (fixed: code depends on them); **active** means open, in progress or waiting. Tasks are **never deleted**: a mistaken one is cancelled, and a done or cancelled task can be reopened. `due_date` is a calendar day in India; `follow_up_at` is when to look at it again (a task with a future one is *parked*); `follow_up_every_days` is the cadence; `follow_up_count`, `last_followed_up_at`, `waiting_on`; `completed_at` and `completed_by` (set together by Done, cleared by any other status; null `completed_by` with a set `completed_at` means the system closed it). `origin` is `manual` or `auto`, with `source_type` (`demo_request`, `invoice`, `license`, `sale_milestone`) and `source_id` for a task raised by the CRM and a `dedupe_key` that is unique where set. **Rules the database enforces:** `waiting` needs `follow_up_at`; `done` needs `completed_at`; `source_type` and `source_id` are both set or both null; an `auto` task needs a `dedupe_key`; lengths and positive numbers are checked. **Urgency (overdue, due today, follow-up due, parked) is never stored**: it is worked out from the dates, in India time, by `src/features/tasks/sections.ts`. A deactivated owner reads as Unassigned (users are deactivated, never deleted, so a foreign key cannot catch it); `TASK_SELECT` does that when it reads |
| `demo_requests` | "Book a demo" submissions from the FactoOne landing page, written by `POST /api/intake/demo-requests` (no staff user involved). `status` new / contacted / scheduled / done / spam, optional `owner_id`, `notes` and `client_id` (set when converted). `external_ref` is unique when present, so a retried submit is the same request; the same email or mobile within 24 hours raises `repeat_count` on the first request instead of adding a row. The visitor's address is kept only as a salted hash (`ip_hash`). Staff move a request between statuses in any order; `contacted_at` is set the first time it reaches contacted, scheduled or done and never cleared. Each status, owner or notes change is an `activity_log` row (`entity_type = 'demo_request'`, no `client_id`); the website's own rows have no actor |
| `company_settings` | One row (`id = 1`): company, state, GSTIN, bank, receipt prefix, defaults, invoice tagline and declaration text |
| `document_sequences` | `(doc_type, scope)` counters: client codes (global), sale orders (per client), quotations and invoices (per client per month, scope `AA01-1026`), receipts (per financial year). Allocated with a row-locking upsert inside the business transaction |
| `sale_item_billing`, `sale_billing` (views) | Derived per-item and per-sale figures: taxable billed (issued vs draft), billed total, paid on invoices, advance, still to bill. Never stored, so they cannot drift |
| `_migrations` | Applied migration files |

## Delete behaviour

`ON DELETE RESTRICT` on everything that carries financial or license history (clients, products, invoices, payments), so history cannot disappear by accident. `CASCADE` only for items owned by a draft/sale (`sale_items`, `invoice_items` of drafts). `SET NULL` for optional user/sale back-references.

## Why not Prisma's suggested model list

The brief listed Lead, FollowUp, Quotation, CreditNote, Deal and similar tables. v1 scope was reduced to clients, sales, licenses, invoices and payments, so: *Deal/DealItem* became `sales`/`sale_items`; *Lead, FollowUp, Quotation, CreditNote* are deferred (nothing in the schema blocks adding them); *DocumentSequence*, *LicenseEvent*, *PaymentAllocation*, *ActivityLog* and *CompanySettings* are implemented as specified; *UserProfile* is the `users` table itself because auth is local rather than Supabase Auth.

## Document numbers

| Document | Format | Counter |
|---|---|---|
| Client code | `AA01`, `AA02` ... `AA99`, `AB01` ... `ZZ99` | One global counter; permanent for the client, assigned when the client is created |
| Sale order | `SL-AA01-01` | Per client, never restarts |
| Quotation | `QT-1026-AA01-01` (QT-MMYY-client-nth) | Per client per month of the sale date; created with the sale |
| Invoice | `INV-1026-AA01-01` (INV-MMYY-client-nth) | Per client per month of the issue date; allocated at issue |

Invoice numbers must stay within GST's 16 characters (CGST Rule 46), so the prefix is fixed (`INV`) and a client can have at most 99 invoices a month; issuing the 100th is refused with a clear message. Sales, quotations and invoices created before codes existed keep their old numbers (`SL-0007`, `DE/2026-27/0001`); only new documents use the new format.

## Follow-up rules (tasks)

A follow-up time is never set when a task is created (only a cadence is copied from the category). A task with a follow-up time still ahead is **parked** and leaves the Desk, even when overdue, until the time comes; the Parked count shows how many are already late. When the time returns, the task shows under Follow-ups due, or stays in Overdue with a follow-up-due tag when its deadline has also passed. `follow_up_count` is a lifetime count of recorded follow-ups (snoozes are not counted); three or more reads **Stuck**. Leaving `waiting` for open or in progress, and reopening a done or cancelled task, clears the return time.
